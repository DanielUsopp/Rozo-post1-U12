# ADR-001: Capas simples para la persistencia; la notificación conserva su interfaz y aísla los fallos entre observadores

## Estado
Aceptado — 2026-11-11

## Contexto
Con Chain of Responsibility (validación), Strategy (cálculo) y Observer (notificación) ya integrados, corresponde decidir si el sistema de solicitudes de reembolso debe migrar a arquitectura Hexagonal completa, con puertos e interfaces intermedias para todas sus dependencias externas, o mantenerse en capas simples. La Guía (sección 6.2) da el criterio: Hexagonal vale la pena en sistemas que sobrevivirán 3 años o más con cambios de infraestructura. La evaluación se hizo por separado para las dos dependencias externas del sistema.

**Persistencia.** `SolicitudReembolsoService` usa directamente `RepositorioSolicitudesJpa` (Spring Data JPA sobre H2). No existe ningún plan de cambiar de motor de base de datos, y el único uso del repositorio son tres operaciones (`save`, `findById`, `findByEmpleadoIdAndEstado`). El dominio ya está libre de JPA, porque el mapeo vive en `META-INF/orm.xml`.

**Notificación.** El servicio no conoce a los notificadores concretos: depende de `List<ObservadorCambioEstado>`. Contabilidad anunció que el próximo trimestre integrará un sistema externo, por API, para programar el pago de las solicitudes aprobadas. Hoy los tres observadores solo escriben en consola o en el log y no pueden fallar; una llamada HTTP a un sistema externo sí puede fallar (tiempo de espera, servicio caído). Como el servicio recorre los observadores uno tras otro con `forEach`, una excepción de Contabilidad cortaría el recorrido y los observadores siguientes, entre ellos auditoría, no se enterarían del cambio. El RF3 exige que auditoría registre "todo cambio de estado, sin excepción".

## Alternativas consideradas
| Alternativa | Persistencia | Notificación |
|-------------|--------------|--------------|
| A. No hacer nada | Igual que hoy | Igual que hoy: un fallo de Contabilidad dejaría a auditoría sin registro |
| B. Hexagonal completa | Puerto `RepositorioSolicitudes` + adaptador JPA + mapper | Puerto `PasarelaPagosContabilidad` diseñado desde ahora |
| C. Elegida | Igual que hoy | Misma interfaz, con cada observador aislado de los fallos de los demás |

## Decisión
**Persistencia: se mantienen capas simples.** `SolicitudReembolsoService` sigue dependiendo de `RepositorioSolicitudesJpa`, sin una interfaz de puerto intermedia. Un puerto hoy sería una abstracción con una sola implementación y sin un caso de uso que la pida (YAGNI). No se cumple el criterio de la Guía: no hay cambio de infraestructura previsto para la base de datos.

**Notificación: no se agrega ningún puerto ni interfaz nueva.** `ObservadorCambioEstado` ya es el punto de extensión que necesita la integración de Contabilidad: `NotificadorContabilidad` podrá llamar a la API externa por dentro sin que cambie el servicio ni los otros observadores. Lo que sí cambia es cómo se notifica: el servicio captura la excepción de cada observador por separado, la registra en el log y continúa con los demás. Así, una falla en el sistema externo de Contabilidad no impide que el empleado y auditoría se enteren del cambio, y el cambio de estado ya guardado no se pierde.

No se diseña desde ahora el contrato con el sistema de Contabilidad, porque ese contrato todavía no existe: cualquier interfaz escrita hoy tendría que adivinarlo.

## Consecuencias
**Positivas**
- No se agregan interfaces, adaptadores ni mappers de persistencia sin un caso de uso real.
- El único cambio de infraestructura con fecha conocida, la integración de Contabilidad, ya tiene su punto de extensión y, además, no puede afectar a los otros interesados ni al registro de auditoría.
- Las reglas de ArchUnit verifican los límites que sí existen (procesamiento sin infraestructura, controlador solo con la aplicación) sin suponer puertos que no hay.

**Negativas**
- Si en el futuro hay que cambiar de motor de base de datos, el puerto de persistencia tendrá que introducirse después, tocando el servicio. Se acepta esa deuda de forma consciente.
- Un fallo de un observador ya no interrumpe la petición, así que puede pasar inadvertido: queda solo en el log. Cuando Contabilidad esté integrada hará falta monitorear esos errores o agregar reintentos; hoy no se implementan porque no hay sistema externo contra el cual reintentar.
- Un revisor que espere simetría total, con puertos para todas las dependencias, puede interpretar la diferencia entre persistencia y notificación como una inconsistencia si no lee este ADR.

## Cuándo revisar esta decisión
- Si se decide cambiar de motor de base de datos o exponer las solicitudes a otro sistema que no sea la API REST, revisar la persistencia.
- Si la API de Contabilidad resulta lenta o poco confiable, evaluar notificación asíncrona (por ejemplo, una cola) en lugar de llamadas dentro de la misma petición.
